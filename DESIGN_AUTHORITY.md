# Agent Factory — Design Authority (SSOT)

> **CRITICAL INSTRUCTION FOR AI AGENTS (Claude, Grok, Gemini):**
> This document is the **single, immutable source of truth** for architectural intent, component contracts, and engineering standards across the Agent Factory and Cartridge ecosystem.
> 
> **Zero Code Modification Rule:** No AI agent may create, modify, or delete any codebase files without first documenting the intent, logging the gap, and acquiring an explicit task lock within this document.

---

## 1. Governance & Hierarchy of Authority

When discrepancies arise between repository documents, prompts, or discussions, the following strict order of precedence applies:

1. **`DESIGN_AUTHORITY.md`** (This Document) — The ultimate arbiter of engineering intent, contracts, and lifecycle.
2. **Machine-Enforced Schemas** (`packages/contract/src/schema.ts`, unit tests) — The concrete validator.
3. **`POSITION_PAPER.md`** — Strategic philosophy, north star, and commercial manifesto. In any technical conflict with this document, `DESIGN_AUTHORITY.md` prevails.
4. **AI Platform Instructions** (`CLAUDE.md`, `GEMINI.md`, Grok system prompts) — Operational guidelines for specific LLMs.

## 2. AI Operating Protocol (Mandatory Workflow)

Every AI session (Claude, Grok, or Gemini) **must** follow this strict state machine before and during any code edits.

```
       [User Declares Intent]
                 │
                 ▼
     [AI Updates Intent in DA]
                 │
                 ▼
  [AI Confirms Update with User]
                 │
                 ▼
    [AI Logs Conflict/Gap in DA]
                 │
                 ▼
    [AI Acquires Task Lock in DA]  ◄── (Other AIs blocked on these files)
                 │
                 ▼
      [AI Modifies & Tests Code]
                 │
                 ▼
 [AI Verifies, Closes Task, & Unlocks]
```

### The 6-Step Workflow:

1. **User Declares New Intent:**
   - The user describes a new feature, behavioral modification, or design correction.
2. **AI Updates Design Authority & Confirms:**
   - **First, cite what already applies and test the boundary.** Before proposing any new rule or design, the AI names the existing invariants (§6) and the user's recorded decisions (§7) that bear on it. If an existing invariant already covers the case, the work is to register and fix the violation, not to add a rule. A proposal that contradicts a recorded decision says so explicitly and asks. Crucially, the AI applies **The Donna Test (Cartridge vs. Factory Boundary Gate)**: verify whether the reported defect is a cartridge concern (an agent's reasoning, chat memory, or tool execution) versus a factory concern (compute lifecycle, network perimeter, secrets binding, or mind storage sync). If another agent (like Donna) already succeeds at the behavior, the platform already supports it; the fix belongs in the cartridge or agent template, never in factory kernel packages.
   - The AI updates the *Declared Architectural Intent* section of this document.
   - The AI explicitly confirms this text update with the user before touching code.
3. **AI Documents the Conflict or Gap:**
   - The AI inspects the codebase against the new intent and logs a specific item in the **Conflict & Gap Register** (Section 4).
4. **AI Acquires a Task Lock:**
   - In the **Active Task & Locking Board** (Section 5), the AI creates or transitions the task to `LOCKED`.
   - The AI records: `AI Model (Claude | Grok | Gemini)`, `Timestamp`, `Session ID / Reference`, and `Locked Scope (Target Files)`.
5. **AI Implements Code within Locked Scope Only:**
   - The AI edits only the files claimed in the lock.
   - If adjacent files require changes, the AI must first expand its lock in `DESIGN_AUTHORITY.md`.
6. **AI Closes Task and Releases Lock:**
   - After testing and verification, the AI sets task status to `COMPLETED`, adds resolution notes, and clears the active lock.

## 3. Lock Recovery Protocol (Handling Hung or Abandoned Sessions)

Because AI sessions can be terminated unexpectedly (token limits, session crashes, timeouts), a strict lock recovery protocol is required:

1. **Detecting a Stale Lock:**
   - An incoming AI session inspecting the board sees a task marked `LOCKED`.
2. **Verification of Work State:**
   - The incoming AI **must inspect the codebase and git status** for the files listed under `Locked Scope`.
   - Case A: *Work was completed but not marked closed.* The incoming AI runs tests, validates against intent, and marks the task `COMPLETED`.
   - Case B: *Work was partially done or never started.* The incoming AI evaluates whether the existing diff is sound or needs resetting.
3. **Formal Lock Transfer (Override):**
   - The incoming AI explicitly logs in the task history: `[TIMESTAMP] Lock taken over from <Previous AI> by <Current AI> due to inactivity/session end.`
   - The incoming AI updates the `Locked By` field to its own identity and proceeds.

## 6. Declared Architectural Intent (The Target State)

### 6.1 The "New Hire" Mental Model (Console vs. Cartridge)
An Agent Cartridge is modeled as a **Digital Employee** being onboarded into an enterprise:
1. **The Job Description & Instructions (`soul.md`):** Persona, responsibilities, tone, and strict behavioral boundaries.
2. **The Employment Contract & Access (`cartridge.yaml`):** Declared variable names for required secrets, trigger events, tool capabilities, and persistent memory prefix.
3. **The Toolbox (`skills` / MCP Tools):** External tools, APIs, or MCP servers placed at the agent's disposal. Skills come from the agent's own code or from approved shared skills it adopts (SK1–SK5).
4. **The Filing Cabinet / Memory (`/memory`):** Embedded file-based databases (SQLite, DuckDB, JSON files) stored in `$MEMORY_DIR` that the Factory Console automatically hydrates on boot and syncs to object storage on sleep. (External shared enterprise databases are accessed via declared connection secrets).
5. **The Performance Rubric & Scorecard (`bench.yaml`):** Deterministic evaluation test cases ("When Y happens, do X; when B happens, do A") used to benchmark accuracy, latency, and token cost across models.
   - **Policy Gate Rule:** `bench.yaml` is **optional by default** at registration and across all stages. Factory administrators can configure company policy gates to require benchmarking at specific lifecycle milestones (registration, deployment, run, or production tier promotion).

### 6.3 Invocation & Runtime Semantics
* **Zero Custom SDK Requirement:** The worker receives its invocation payload via standard input environment (`FACTORY_INPUT` / `/tmp/input.json`), or clean invocation handler, and outputs its result without needing bespoke REST polling loops.
* **Perimeter Defense:** The Cartridge never holds a public IP address or directly opens unauthenticated public ports. Everything that crosses the perimeter, in either direction, is the Gatekeeper's job (P1).
* **P1 – The Gatekeeper owns the perimeter.** It is two services. `gatekeeper-ingress` carries everything that reaches an agent: Discord presence, webhooks and other triggers, and the wakes they cause. `gatekeeper-egress` carries every outbound connection an agent makes (E1–E8): routes, hosts, models, metering and credential injection. The two deploy and scale separately, so a fault in one never cuts the other. Presence tells the truth: an agent shows available (online) only once its run is ready to take a turn, which is its first heartbeat or mailbox poll from inside the container; while a wake is in progress it shows starting, never available. No other component carries agent traffic across the perimeter.
* **P2 – One name for the perimeter.** `Gatekeeper`, `gatekeeper-ingress` and `gatekeeper-egress` are the only names the factory uses for its perimeter, in code, packages, images, services, infrastructure, configuration, environment variables, agent repositories and documentation. No alias, compatibility name or superseded identifier remains. Third-party proper names are not the factory's (for example Discord's Gateway API, a cloud NAT gateway). Only append-only history keeps what it recorded: ledger rows (§6.10) and §7 entries written before a rename.
* **Network & gatekeeper-egress Security:** See the egress invariants below. They apply to every provider and every cloud; there are **no exceptions**.

#### 6.3.1 Egress Invariants (each has a conformance test, §6.7)
* **E1 – Single egress path.** Every outbound connection from cartridge code goes through the gatekeeper-egress. No exceptions, including cloud-provider APIs. An agent's `NO_PROXY` may contain only loopback, `.internal` service discovery, and the link-local metadata/credential addresses.
* **E2 – Run attribution.** Every gatekeeper-egress request carries the run's short-lived token; requests without a valid, live run token are rejected.
* **E3 – Ledgered.** Every egress request or tunnel writes a ledger row (agent, run, route or host, allow/deny decision) — never prompt bodies or secrets.
* **E4 – Gated before forwarding.** The gatekeeper-egress enforces policy (routes, hosts, models), budget, pause/isolate/kill switch, and approvals before any byte leaves.
* **E5 – Every model call is metered.** Agents may use any model provider (Anthropic, OpenAI, AWS Bedrock, xAI, …), but every model call goes through a gatekeeper-egress **provider route** so tokens and cost are metered and ledgered. A cloud model service (e.g. Bedrock) is a gatekeeper-egress upstream configured by the landing zone; the gatekeeper-egress holds the cloud credentials, cartridges never do. A generic CONNECT tunnel is **not** an acceptable path for model calls, because it cannot meter tokens or cost.
* **E7 – Deny by default.** An agent with no admin-set policy has no egress. The control plane never grants routes, hosts, models, or budgets on its own (not at registration, not at run start). Only explicit admin actions change a policy: `PUT /api/v1/agents/:id/policy`, model approval, and the global policy. A cartridge's declared egress is a *request* shown to the admin, not a grant, and it bounds any grant (E8). Granting models is such an admin action: an agent with a policy of its own reaches the factory model API (the `models` route) without a separate route grant, and which models it gets is decided only by the policy's models (M2). The global fallback policy implies nothing, and provider-native routes (M4) stay explicit grants.
* **E8 – Declared is the ceiling.** An agent's repository declares everything it needs to do its job: every ingress trigger, every system it reaches and each action it takes there (method and path, E11), every host, model and tool, and every credential, including the ones the Gatekeeper injects for it. A policy may grant only what the admitted commit declares plus the requirements of skills an admin has approved for this agent (SK3), and the control plane refuses a policy that grants more. A new ability means a change in the repo or an approved skill adoption, then admission and a redeploy of that configuration. The Keymaster reports and accepts only declared credentials, and the Gatekeeper serves only declared, granted actions.
* **E9 – Acting as a person waits for that person.** A request an agent makes in a person's name that others will see (a post, a comment, a message) is held, not sent. Which actions are held is declared by the author of the skill that takes them (or, for an agent's own code, in its cartridge), per action (E11). An admin reviews that declaration when approving the skill version or admitting the agent and may change it, and may change any grant's hold at any time, effective on the next request. There is no factory default: an action is held only if its author declared it or an admin set it; the skill review shows every write action that is not held, for information. An agent can never change a hold. The gatekeeper-egress forwards nothing; the control plane keeps a reviewable copy of exactly what would be sent (never a credential, which the gatekeeper-egress injects only on release) and shows it to approvers. Approval releases that request once and unchanged: the agent sends the identical request again and the gatekeeper-egress forwards it; anything different is a new request and is held again. Rejection, with or without notes, sends nothing. The decision is delivered to the agent (its mailbox, or a new run), so a review can take as long as the person needs and no run waits for it.
* **E10 – Systems are factory data.** Every external system an agent reaches, other than model providers (§6.9), is defined once in the factory: where requests go (upstream), the credential kind (static secret or OAuth connection) and how it is injected, and for OAuth the sign-in URL, token URL, token behaviour (refresh or expiry) and scopes, and the factory's own app registration with that system (its client secret held by the Keymaster, K1). An admin approves each definition once per factory, and it takes effect without a platform change or a redeploy. Agents and skills name a system; they never supply an upstream, a sign-in URL or an injection rule. Neither `agent-factory` nor any ops repository holds a list of systems.
* **E11 – Every agent–system pair is a grant.** A grant names the agent, the system, the actions it may take there (method and path, from the agent's admitted declaration and its approved skills, E8), whether each action is held (E9), and the credential it uses: the agent's own, or a named shared one (K5.5). A policy owner approves every grant, shared system or not. The gatekeeper-egress forwards only granted actions and refuses and ledgers every other request to that system. It reads definitions and grants from the factory and caches them; a change applies to the next request without a redeploy.
* **E6 – Network-enforced.** Agent subnets have no internet or NAT route. Platform traffic that is not cartridge code (image pulls, logs, the shim's memory sync) may use private cloud endpoints.

#### 6.3.2 Secrets Invariant
* **S1 – Agents never hold real secrets.** A cartridge's declared secrets are delivered to it only as placeholders (its run token). The gatekeeper-egress injects the real credential into the matching outbound request, based on the route or host the secret is declared for. Secrets that must be used locally (key files for signing, form logins) get a gatekeeper-side exchange route instead, added per secret under a task; until a secret is converted it is listed in the Gap Register. As a backstop, the control plane and gatekeeper-egress redact every known secret value from results and ledger rows, for every runtime; the control plane caches secret values so this does not add a vault lookup per wake.

### 6.4 Two-Stage Agent Retirement Lifecycle (Zero Ongoing Cost Guarantee)
* **Objective:** Guarantee that retired agents incur strictly $0 in continuing cloud costs while providing safety against accidental operational destruction.
* **Stage 1: Soft-Retirement / Scream Test (`RETIRED_PENDING_PURGE`):**
  - All ingress triggers, gatekeeper-ingress presence gatekeeper-egress instances, and compute wakes are immediately cut. Compute drops to 0 replicas.
  - Secret bindings and persistent memory remain in place.
  - An administrative holding period (configurable, default: 1 calendar week) begins.
  - An operator can invoke `POST /api/v1/registry/agents/:id/reinstate` during this period to restore the agent to production.
* **Stage 2: Permanent Purge & Archival (`RETIRED`):**
  - Triggered after the holding window expires or via administrative override (`POST /api/v1/registry/agents/:id/purge`).
  - Cloud task definitions and compute services are deleted.
  - Secrets are permanently destroyed/purged from the enterprise vault.
  - Persistent mind storage is compressed and archived into cold tier object storage.
  - Immutable execution ledger rows remain permanently preserved.

### 6.5 Headless Observability & GraphQL Telemetry Surface
* **Strict Separation:** The Factory kernel never builds UI dashboards, formats PDF reports, or renders email summaries. It strictly captures structured data and serves it via headless APIs.
* **Core Metrics Pillars:** Cost (USD spend, token burn), Quantity (task throughput, turns, duration), Quality (deterministic benchmark pass rates, regression ledger).
* **API Surface Division:**
  - **REST:** Discrete operational actions (`/runs`, `/wake`, `/pause`, `/metrics`).
### 6.6 Agent Memory Architecture ("The Notebook & Safe")
* **Separation of Concerns:**
  - **Cartridge (The Employee):** Strictly reads and writes to local embedded files (SQLite) in `$MEMORY_DIR` (`<agent>_state.db`). Cartridges **never** import cloud SDKs (`boto3`, `@google-cloud/storage`, Azure Blob SDK) and never know about cloud storage buckets.
  - **Console (The Building Safe):** Handled transparently by `packages/hydrate/src/shim.ts`. On wake, the Console pulls remote mind storage (`s3://...` / `gs://...`) into `$MEMORY_DIR`. On sleep/exit, the Console pushes `$MEMORY_DIR` back to the remote mind bucket.
* **SQLite Storage Engine Standards:**
  - **WAL Mode:** Every cartridge SQLite database must execute `PRAGMA journal_mode=WAL;` and `PRAGMA busy_timeout=5000;` on connection.
  - **Single-Writer Clean Checkpointing:** Cartridges execute `PRAGMA wal_checkpoint(TRUNCATE)` in their shutdown/exit cleanup (`finally:` block). This collapses the `-wal` and `-shm` write-ahead logs into the primary `.db` file, guaranteeing clean, atomic object storage synchronization without lock artifacts.
  - **Rolling Retention Pruning:** Raw chat turns and audit entries must have rolling retention (default 14 days) pruned automatically on wake to prevent boundless context database growth. Permanent knowledge (entities, facts, operational logs) is retained indefinitely.
* **Private Agent Memory Isolation:**
  - Cartridge memory is **strictly private** to each agent. Agents never share SQLite databases or object storage mind prefixes.
  - Cross-agent collaboration and knowledge sharing is strictly conducted via the gatekeeper-ingress (MCP) (`talk_to_agent`), preserving encapsulation, provenance, and auditability.

### 6.8 Two Lifecycles: Platform and Agents
* **L1 – Platform.** Each deployment target (AWS, GCP, Azure, private cloud, …) has its own ops repository, which pins an exact `agent-factory` commit and deploys it through that repository's CI, run manually on its `main`. `agent-factory` knows nothing about any particular deployment. A platform deploy never adds, removes, or changes agents. An ops repository holds no systems, routes, grants, model catalog or secrets (E10, E11, M3, K5).
* **L2 – No agents in the platform repo.**
* **L3 – Admission gate.** An agent owner registers an agent by naming its repository; admission applies to the agent's whole deployment configuration (SK3, SK4): its source and its adopted skills. The factory pins the exact commit and runs the equivalent of CI against it: validate `cartridge.yaml`, build the image, run the agent's own tests (a repository without tests is refused), and check the design rules (§6.6, S1, declared secrets and egress). A failure refuses registration with the reasons, and the refusal is ledgered.
* **L4 – Gated deploy.** An agent can deploy only after a policy owner (e.g. FinOps) has set its policy and budget (E7). The deploy itself may be done by the agent's owner, an admin, or the factory under a policy that allows it. The factory deploys exactly the admitted configuration (SK4): an image built from the pinned source and pinned skills, tagged by the configuration's hash, never a mutable tag.
* **L5 – New versions.** The factory notices new commits on a registered agent's repository, and changes produced by factory training, and runs each through admission (L3). A version that passes shows as "new version available". It goes live only after a person approves it, unless a person has set a policy allowing that agent's admitted versions to deploy automatically.
* **L6 – Agent template.** `agent-factory` provides the template agent builders start from, including a passing test and the admission requirements. It is documentation and scaffolding, not part of any deployed image.
* **Test fixtures** (such as the echo and summarizer cartridges) are equipment for the platform's own tests. They are not agents and never appear in a factory's agent list. A platform deploy's definition of done proves the agent lifecycle by registering a test cartridge through L3–L4, making one gatekeeper-egress-metered call, and retiring it.

### 6.9 Model Access
* **M1 – One factory model API.** Agents call models through the gatekeeper-egress using the factory's model API: the OpenAI Chat Completions request format, documented for agent builders. Agents never call a provider directly and never hold provider credentials (E1, E5, S1).
* **M2 – Preferred, not chosen.** A cartridge declares a preferred model. The model an agent actually gets is decided by policy (E7); operations may substitute any offered model without changing the agent. A policy that names no models grants exactly the factory's default model (Claude Haiku 4.5 unless operations configure another), never every model.
* **M3 – Operations decides the offering.** Each factory's offering (provider, the provider's model id, price) is factory data that admins maintain, changed without a redeploy; provider keys are supplied through the Keymaster's platform credentials, and a landing zone supplies only cloud permissions (for example the gatekeeper-egress's access to a cloud model service). A preferred model the factory does not offer is shown as a request. Agents never get a route to a model provider other than the gatekeeper-egress's provider routes (E5). The gatekeeper-egress translates the factory model API into each provider's native format and meters every call the same way, whatever the provider.
* **M4 – Native access is an exception.** An agent that genuinely needs a provider-specific feature may declare that need and use the provider's native format through the gatekeeper-egress, still metered and policy-gated. Such an agent is provider-dependent, and its admission shows that.

### 6.10 Ledger Integrity
* **LG1 – Single writer.** Exactly one control-plane process writes a ledger at any time, enforced twice: the control plane holds an exclusive, renewed lease on the ledger before it starts (a second instance refuses to start and says why; a lease left by a crashed instance expires after a short timeout), and every landing zone deploys the control plane stop-then-start, never side by side. A control-plane deploy therefore has a brief gap (accepted 2026-09-28); running concurrent control planes would require moving the ledger off a shared file.
* **LG2 – Never edited.** A ledger that fails verification is archived unchanged as evidence, never repaired in place. Recording continues in a new segment whose first entry chains to the last verified checkpoint and records the recovery (why, and what was archived).

### 6.11 Keymaster: Credentials That Act for a Person or an App
* **K1 – The Keymaster owns them.** OAuth grants, refresh tokens, and app client secrets are held only by the Keymaster. Agents declare the *connections* they need (system plus scopes) in their cartridge; admission shows them; the agent never holds the credential. How each provider's sign-in and tokens work comes from its approved system definition (E10), never from agent or platform code.
* **K2 – Consent happens in the factory.** A person connects an agent to a provider through the factory. The provider redirects back to the factory; the Keymaster stores the grant scoped to agent × provider × scopes; the ledger records who granted what, and when.
* **K3 – The Keymaster refreshes; the gatekeeper-egress injects.** The agent calls a gatekeeper-egress route; the gatekeeper-egress obtains a current access token from the Keymaster (which refreshes and persists rotated tokens) and injects it.
* **K4 – Broken consent is reported, never worked around.** A revoked or expired grant is marked "needs re-consent". A provider that issues no refresh token (LinkedIn) gives a grant that ends when its access token does; the Keymaster reports when it ends, so the person can reconnect before then, and marks it at expiry; the agent is told so and directs the person to the factory's reconnect link. Agents never ask a person to run scripts or handle credentials.
* **K5 – The Keymaster facilitates every credential an agent needs.**
  1. *Declared at registration.* An agent declares every credential it uses, each with its kind (static secret or OAuth connection), the source system it comes from, and scopes where they apply. This includes the credentials the Gatekeeper uses on the agent's behalf: each trigger's `secretRef` and each per-agent route credential (`{agent}_X`). An agent declares a logical name; the Keymaster creates and names every entry itself (`agents/<agent>/<system>/<name>` for an agent's own credential, `shared/<system>/<name>` for a shared one), so an agent cannot name another agent's credential or a platform key. From the declaration the Keymaster knows where the credential is stored and how it is obtained (E8).
  2. *Outstanding credentials are known.* The Keymaster compares each registered agent's declarations with what is present and valid in the secret manager. A credential that is missing, lacks declared scopes, or needs re-consent is outstanding for that agent.
  3. *One flow, every surface.* The Keymaster API is the flow; the dashboard and the Garrison interface are clients of it and add no logic of their own. In each, the owner picks an agent and sees its outstanding credentials, each with instructions for creating it and a way to supply it: OAuth through a consent URL whose callback lets the Keymaster store the grant; static secrets (for example GitHub PATs, Discord bot tokens, Slack keys, API keys) through a write-only input the Keymaster writes to the secret manager. A supplied value is never displayed, echoed, logged, or ledgered; the ledger records only that it was set or rotated, by whom, and when.
  4. *Instructions come from a reviewed catalog.* The Keymaster keeps a catalog of instructions per source system, maintained by operations. Entries may be AI-drafted; a person reviews and approves each one. Until then an entry is shown to owners clearly labelled "Pending human review", never presented as approved.
  5. *Access is policy, not possession.* A credential may serve several agents (for example one workspace integration). Because agents never hold it (S1), which agents may use it is decided by factory policy (routes and agent state), not by who has the value: revoking one agent's access (pause, decommission, destroy, or removing the route) never requires rotating the credential, and rotating a credential never involves an agent.
  6. *Addressed to the agent owner* (an owner and an admin may supply an agent's credentials; owner rights are the Bouncer's, GAP-088). No one is asked to run a script or to put a secret in a chat, terminal, or repository.


### 6.12 Operator Access
* **A1 – One front door.** The factory's public endpoints accept connections only from its identity-aware proxy (Cloudflare Access on AWS); the load balancer refuses all other sources. Machine callers (deploy checks, webhooks) use the same door with a service credential. No landing zone opens platform ingress to `0.0.0.0/0`.
* **A2 – Identity is verified, not asserted.** The control plane grants a role only from a credential it verifies cryptographically: a factory token, a run token, or the proxy's signed assertion checked against its issuer and audience. An identity header alone grants nothing, and no proxy (the console included) adds a privileged credential on a caller's behalf.


### 6.13 Recoverability
* **R1 – The factory's own state is recoverable.** Everything only the factory holds (agent registrations and deployment configuration, policies, approvals, schedules, runs) is backed up automatically and can be restored to an earlier point in time. The ledger (§6.10), credentials (§6.11) and agent memory (§6.6) keep their own protection. Restoring is a documented operation, rehearsed at least once. The deployment configuration store (SK3) is versioned with point-in-time restore and can be exported.


### 6.14 Skills and Deployment Configuration
* **SK1 – Skills are registered, admitted and approved.** Any authenticated user may register a skill by naming a repository, a path and a commit: one repo per skill, a skills monorepo, or a folder inside an agent's repo. A skill is its source: a different repository or path is a different skill, never a new version of an existing one. Admission pins the commit, runs the skill's tests and checks the design rules (no secrets, no direct hosts, no provider SDKs). Every version, not just the first, is approved by a factory admin before agents can use it, and, as a pull request merges only when its required checks pass, only after the factory has built it, run its tests and checked its code against these rules. Revoking an approved version that any agent's deployed configuration uses is refused until those agents are redeployed without it; an admin override revokes it at once and pauses every agent using it until each is redeployed without it. Refusals, approvals and revocations are ledgered.
* **SK2 – A skill declares what it needs and holds nothing.** A skill's manifest declares the routes, connections (with scopes), credentials and models it requires. A skill never holds a secret (S1) and never grants access; what it can do inside an agent is bounded by that agent's policy (E7). Enforcement is per agent; a skill that must be isolated from its host's other grants runs as a separate service with its own identity.
* **SK3 – An agent's deployment configuration lives in the factory.** Each agent has one versioned configuration record: its pinned source (repo and commit), the skills it has adopted (each pinned to an approved version), and its policy. Every change creates a new version recording who, when and why, and is ledgered with a content hash. Adopting, upgrading or removing a skill is a configuration change, not a code change. The agent's owner can view the configuration, adopt, upgrade, hold or roll back skill versions, and export it; any of those that adds access needs a policy owner's approval (E7).
* **SK4 – What runs is exactly the configuration.** Applying a configuration builds one image from the agent's source at its commit plus each adopted skill at its pinned commit, tagged by the configuration's hash, admitted and deployed (L3, L4). No code is ever loaded at runtime. An agent's request in conversation to adopt a skill creates a request in the factory that a person approves.
* **SK5 – New skill versions are offered, never forced.** When a newer approved version of an adopted skill exists, the factory shows "skill update available" to the agent's owner (as L5 does for agents). The owner decides when to upgrade.

### 6.15 Factory Service Architecture (The Cast of Characters) & First-Class Contracts
* **SV1 – Intentional Services.** Every workspace package belongs to one of the 11 recognized services (Gatekeeper, Keymaster, Tinman, Secretary, Landlord, Auditor, Treasurer, Bouncer, Timekeeper, Registrar, Seer), to declared platform tooling (`console`, `conformance`, `bench`), or to a declared reservation for a named service that has no implementation yet (`budget` for Treasurer, `triage` for Seer). A service's `hostedIn` entries are workspace packages that contain its implementation source; a directory that merely exists is not a host. Introducing a new service requires explicit architectural intent, naming the new cast member, and user confirmation before implementation. Incidental or stealth service creation is prohibited.
* **SV2 – First-Class Cross-Service Contracts.** Services communicate across boundaries strictly through explicit, typed contracts wired directly into real call sites. Direct backdoor access to another service's private persistence, tables, files, or internal modules without a formal contract is forbidden.

#### The 11 Factory Services (The Cast):
1. **Gatekeeper (Perimeter Security):** Owns inbound presence, wakes, webhooks, front-door authentication verification (A1, A2), and zero-trust outbound proxying (E1, E6) with credential injection (S1). Composed of `gatekeeper-ingress` and `gatekeeper-egress`. It authenticates and never authorizes: `packages/auth` verifies a credential and yields a principal with its roles (A2), and the identity links an admin sets (a Discord user to a person) are its data; what a principal may do is the Bouncer's.
2. **Keymaster (Credential Facilitation):** Owns OAuth connections, consent flows, token refreshes (K1–K4), write-only static secret onboarding (K5), and vault mapping.
3. **Tinman (Model Service / Inference Provider):** Provides the uniform OpenAI-compatible Chat Completions API (M1), translates calls to model providers (Bedrock, OpenAI, Anthropic, xAI), enforces model policy routing (M2), and counts tokens (E5); it reports each call's usage and the Treasurer prices it and decides standing.
4. **Secretary (Hydration & State Store):** Enforces "The Safe" (§6.6); syncs local SQLite databases in `$MEMORY_DIR` with cloud object storage on wake and sleep, ensuring cartridges never require cloud storage SDKs.
5. **Landlord (Compute Lifecycle & Turn Broker):** Manages serverless min=0 compute, wake-from-zero, warm-down windows, operational pause/kill-switches, turn coordination via `/mailbox` long-polling, and two-stage retirement (§6.4).
6. **Auditor (Immutable Ledger):** Owns the cryptographic append-only WORM audit trail of runs, spend, credential actions, and perimeter decisions (LG1, LG2) with automatic secret and prompt redaction.
7. **Treasurer (Spend Governance & FinOps):** Owns the budget rule in `packages/budget`. `checkStanding` is the typed contract for whether an agent is inside its limits (unacknowledged spend included when the caller has it). `packages/budget` holds the budget rule, spend accounting, pricing and the standing contract. The gatekeeper-egress asks before every model call, the Landlord asks before every wake (`createRun`), and the control plane asks on ledger ingest and on a policy update. Those callers enforce the answer (`budget.alert`, `blockRun`, HTTP 402); the Gatekeeper's ingress relays a refused wake to the person. A conformance test fails if the gatekeeper-egress or control-plane source compares spend with a limit itself.
8. **Bouncer (Authorization & Approvals):** `packages/bouncer` decides who may do what and holds what must wait for a person. Authorization is role-based in every case: a user maps to roles and a role maps to privileges, never a user to a privilege, and the table is built into the code (making it factory data an admin edits is a later enhancement). Every control-plane route asks the Bouncer for one named privilege (`authorize`, `requirePrivilege`); the roles are the six `auth` emits plus two derived from data, never from a credential: `agent-owner` (a person on the agent's configuration record, SK3) and `requester` (the person whose message started a run, set only by the ingress). An owner may wake, pause and resume the agent, view and export its configuration, supply its credentials and start its connections, and decide its held actions when the run has no requesting user. For an agent's action the agent is the actor and the requesting user is the reviewer and approver; the global `admin` and `approver` roles also decide any agent's. The Bouncer also owns the approval record and the E9 hold rules (the reviewed copy, its hash and size limit, which requests are held and which tool calls need approval); the gatekeeper-egress asks it and enforces the answer, and the control plane acts on a decision (`blockRun`, `deliverDecision`). Conformance fails on a role check outside `packages/bouncer` and `packages/auth`, on a privilege that is not in the contract, and on a route the matrix test does not list (`packages/conformance/src/authorization.test.ts`).
9. **Timekeeper (Scheduling & Timers):** Manages agent-scoped cron schedules and one-shot wakeup timers without requiring persistent in-container daemon processes.

#### Architectural Boundaries:
* **The Cartridge vs. Factory Boundary ("The Donna Test"):** Cartridges (the employees) own business logic, prompts, persona, and internal cognitive reasoning loops. The Factory provides the utilities (compute, memory safe, model service, perimeter).
* **The Console vs. Factory Boundary (Headless Principle):** The web Console and Garrison are headless client overlays (§6.5). They own zero service logic, zero secrets, and zero persistence.
