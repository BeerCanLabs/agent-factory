# Factory auth plan: requirements, decisions, stories

Companion to [factory-auth.json](factory-auth.json). Source: Page "Agent Factory: authorization and login redesign" (owner Dale Sackrider), Nov 1, 2026; updated with Dale Sackrider's product-flow walkthrough decisions on Nov 1, 2026.

## Intent

The IdP answers only "who is this?". The factory answers "what may they do?": principals (with 1..N verified emails), domain rules, roles, grants and checks live in factory storage, enforced in factory code. The factory is headless with one way in, its API; console, MCP, CLI and desktop are clients of it.

## Requirements

- **R1** The control plane derives no role from Access claims, env email lists, or headers.
- **R2** Principals and grants are stored durably (same backend as the config store, S3 on AWS), versioned, and survive restarts.
- **R3** Grant subjects: principal (`user:<id>`), email domain (`domain:<domain>`), or group (`group:<id>`). Grant scopes: fleet (role on the factory), agent (`content-owner`, `accountable-lead`, `member`, or agent sub-role), skill (`content-owner`).
- **R4** Grant, revoke and list are API endpoints guarded by `grants.manage` (plus scoped `content-owner` and `accountable-lead` delegation rules); clients add no logic of their own.
- **R5** Every route-enforcement authz decision and every grant/principal/key change is written to the ledger with actor, `onBehalfOf` (when an admin acts as another user), subject, scope, before and after. Read-only UI preflight calls to `GET /api/v1/authz/check` do not emit denial noise to the ledger.
- **R6** Machine and device credentials are factory API keys: shown once, stored hashed, with scopes, optional expiry (`expiresAt: string | null`; non-expiring keys allowed), and owner (`user:<id>` for person device keys or `service:<name>` for machine-only roles); revocation is immediate.
- **R7** `GET /api/v1/whoami` returns `{ principal, emails, grants, privileges }`; `GET /api/v1/authz/check` answers a single side-effect-free question (`{ allowed, requiredRole }`) for clients.
- **R8** Deny by default; on any store failure, fail closed.
- **R9** Bootstrap, break-glass, and lockout recovery need no Cloudflare login and print no secret.
- **R10** Conformance tests forbid new reads of `FACTORY_ADMIN_EMAILS`/`FACTORY_TOKENS` and require every route to declare a privilege.
- **R11** Trusted IdPs are a first-class setup value chosen by the day-zero admin, never hardcoded; starter set Google, Meta, Cloudflare (plus OIDC providers behind the same adapter interface so Microsoft/others can be configured).
- **R12** Configured IdPs and optional per-IdP `allowedDomains` (`string[] | null`, default `null` so consumer Gmail/Hotmail/Meta accounts work alongside custom domains) are per-deployment configuration (`submind-aws`, `submind-gcp`, any vendored copy), stored with factory config, readable via the API, and changed only by an admin with a ledger entry.
- **R13** Only assertions from configured IdPs with `email_verified: true` (and matching `allowedDomains` when set on that IdP) are accepted; assertions from unconfigured IdPs or with unverified email claims are refused even if a proxy admits them. Domain-wide authorization is expressed as `domain:<domain>` grants in the grant store.
- **R14** No route answers without a credential except the login page; the factory enforces this whether or not a proxy sits in front.
- **R15** One route-exception registry names every non-session route (login page, OAuth callbacks, webhooks) and how each is protected; a conformance test refuses any route outside it that declares no privilege.
- **R16** Webhook handlers fail closed: no configured signature secret means every delivery is refused.
- **R17** Health, version and metrics answer only to a verified machine API key; load-balancer probes use a private listener or a key.
- **R18** The login page lists exactly the IdPs configured at setup and is the single source of truth for web and CLI sign-in.

## Decisions

- **D1 Access is identity-only.** A verified Access or OAuth assertion yields an authenticated identity with zero roles. Roles come only from the factory grant store (direct principal grants, group grants, and `domain:<domain>` grants).
- **D2 One principal per person, 1..N verified emails across IdPs (updated Nov 1 walkthrough).** Each person has one canonical principal (`user:<id>`, display name) mapped to one or more globally unique lowercased emails (for example, Stephanie's principal maps both `stephaniesackrider@hotmail.com` and `stephanie.sackrider@gmail.com`). Any configured IdP assertion with `email_verified: true` matching any email mapped to that principal resolves to that principal regardless of which IdP they used; unverified email claims are refused. Old `cloudflare:` and `oidc:` actors migrate to principals indexed by lowercased email.
- **D3 Factory API keys replace FACTORY_TOKENS (updated Nov 1 walkthrough).** Hashed, scoped keys with optional expiry (`expiresAt: string | null`; non-expiring keys allowed) issued and revoked through the API. Person device keys are owned by `user:<id>` and live-intersected with the owner's current grants on every request; infrastructure keys (`ingest`, `gatekeeper-egress`, `gatekeeper-ingress`, `break-glass`, health probes) attach to admin-managed `service:<name>` principals so human admins continue not holding exclusive perimeter-attestation roles directly.
- **D4 One Bouncer call per request.** Every route asks `authorize()` with the loaded grants; env-based admin checks are deleted.
- **D5 Bootstrap once, API thereafter, plus out-of-band cloud recovery (updated Nov 1 walkthrough).** `FACTORY_BOOTSTRAP_ADMIN` seeds the first admin grant only when zero admins exist; afterwards it is ignored. The API refuses to delete or downgrade the last active human `admin` (`409`). Separately, the out-of-band cloud IAM recovery command (`bcl-aws`) works any time an operator holds cloud IAM access—even when an unreachable admin grant still exists—appending `LOCKOUT_RECOVERED` to preserve the ledger hash chain.
- **D6 Unknown person gets nothing; domain grants materialize on first login (updated Nov 1 walkthrough).** Authenticated callers with no matching principal email and no matching `domain:<domain>` grant receive `403` everywhere except `whoami`, with zero writes (`viewer` is a grant, not a default). If `domain:<domain>` holds an active grant (for example `domain:sackrider.org` -> `viewer`), first verified sign-in under `@sackrider.org` creates that person's principal automatically and applies the domain's grants; revoking the domain grant removes domain-derived access immediately.
- **D7 Role set, with one content-owner grant (Nov 1).** Roles: `viewer`, `operator`, `approver` (admission gate only), `admin`, `budget-owner`, `content-owner` (scoped to a personal agent or skill), `accountable-lead` and `member` (scoped to a team agent), and machine-only `ingest`, `gatekeeper-egress`, `gatekeeper-ingress` held by `service:<name>` API keys. The derived `agent-owner` and `skill-owner` roles collapse into `content-owner`; the privilege table stays, with content type in scope.
- **D8 Open door, grants decide (Nov 1).** Configured IdPs admit verified identities; admission to anything in the factory is a factory grant (principal, group, or `domain:<domain>`). Dale never edits Cloudflare to onboard.
- **D9 API keys bypass Access on /api/v1 and /mcp (Nov 1).** Per-key hashed, scoped credentials (with optional expiry) replace the shared Access service token and `FACTORY_TOKENS`. A retained Access service token only passes the door, zero authority. Fail-closed on grant-store errors covers the lost defense in depth.
- **D10 Admin-only fleet grants in v1; admins can act as any user (updated Nov 1 walkthrough).** Fleet role grants and `domain:<domain>` grants are admin-only in v1. Admins can act as any human user on the system (minting/rotating/revoking device keys, submitting content, managing transfers, or acting via Console/CLI/MCP `actAs`), always recording both `actor` (the admin) and `onBehalfOf` (the target principal) in the ledger.
- **D11 Two agent types; team leads manage team members (updated Nov 1 walkthrough).** Personal assistants (`kind: "personal"`) have exactly one `content-owner` (unique constraint). Team agents (`kind: "team"`) have no owner, one `accountable-lead` grant (appointed/replaced by `admin`), and `member` grants; the `accountable-lead` may add and remove `member` grants (for already-known principals and groups) on their own team agent.
- **D12 Transfer is for life events (Nov 1).** Personal agent owner is the submitter (or target user when an admin acts on their behalf). Transfer (personal agents and skills) is a dedicated two-phase endpoint for departures and promotions, not bootstrap. Provisioning or configuring an agent needs operator/admin config and model grants, not ownership.
- **D13 Pre-grant boundary for unknown principals (reconciled with D32 in Nov 1 walkthrough).** Only **admins** may pre-create principals or pre-grant unseen valid emails (and `domain:<domain>` grants). **Content-owners** and **team leads** (`accountable-lead`) may grant only to principals and groups already known in factory state; mistyped or unknown targets from non-admins are refused before write (`403`, no orphan ledger entry).
- **D14 Channels are a client problem; one key per device family (Nov 1).** A person reaching Higgins via Discord today (identity link) or a Tesla tomorrow holds the same grants; Higgins runs inside the factory and does not authenticate. One active API key per `(owner, deviceFamily)` (for example Stephanie's `"tesla"` key, scoped to `higgins`, non-expiring or expiring). Rotation supports an optional short `graceSeconds` overlap on the same key record so devices update without downtime.
- **D15 Read-only while pending; purge OAuth & outgoing-owner private skills on accept (updated Nov 1 walkthrough).** On a personal-agent or skill transfer the old owner drops to read-only when the pending transfer starts (7-day sweeper TTL). On decline, cancel, or sweeper rollback: old owner's write access is restored non-destructively. On accept: new owner gets write and old grant is revoked; for personal agents, all `oauth-user` tokens (`ConnectionKeymaster`) on that agent are automatically purged (ledgered) and any private skills still owned by the outgoing owner are detached (D26), while non-OAuth static agent secrets (`credentials.agent.*`) stay intact unless changed.
- **D16 IdP is a setup value, per deployment (updated Nov 1 walkthrough).** The day-zero admin chooses which IdP(s) the factory trusts during initial setup (starter set: Google, Meta, Cloudflare, plus OIDC); `allowedDomains` per IdP is optional (`null` allows any verified email from that IdP, with `domain:<domain>` grants and principal grants controlling access). Applies to `submind-aws`, `submind-gcp` and any vendored deployment.
- **D17 Skill-driven egress is a follow-on epic (Nov 1).** Wiring skill routes into agent policy is out of scope for this epic and tracked as the linked follow-on epic, Skill-driven egress policy.
- **D18 No unauthenticated endpoints (Nov 1).** The factory itself enforces it, not the proxy. The only deliberate open route is the human login page; its OAuth callbacks are state-protected, not open. Every other route needs a session, a verified API key, a run token, or a verified webhook signature.
- **D19 Factory-served login page and session (Nov 1).** Web users land on the factory's own login page with one button per IdP configured at setup (D16). After OAuth the factory issues its own session. Cloudflare Access becomes optional, one IdP among others.
- **D20 CLI signs in through the login page (Nov 1).** `factory login --url <factory-base-url>` opens the login page in a browser; the callback returns a `"cli"` device-family credential to the CLI on a local loopback port.
- **D21 Retire the CLI discovery file (Nov 1).** `GET /.well-known/factory-cli` (`control-plane/src/app.ts:2058`, built from `FACTORY_OIDC_*` in `auth/src/discovery.ts`) is retired; CLI login uses the login page directly without a pre-credential fetch.
- **D22 Named exceptions, failing closed (Nov 1).** Health and version need a machine API key (or private internal listener for LB probes). GitHub and generic `/api/v1/hooks/:id` webhooks are signature-verified exceptions that refuse every delivery when no signature secret is set. OAuth callbacks stay state-protected. `/ui` and console SPA assets are served only to a signed-in session; the login page carries its own minimal assets.
- **D23 Unverified keys refused first; /mcp included (Nov 1).** A request presenting an API key is verified before any other handling and refused on failure. `/mcp` uses the same key path as `/api/v1` and filters `tools/list` to the caller's live privileges.
- **D24 Content-owner rights are fixed (Nov 1).** Ownership is metadata naming which personal agents or skills a person controls. Rights: version, configure, decommission, transfer, and grant content roles on that item to already-known principals/groups.
- **D25 One budget-owner per factory; admin is backup (Nov 1).** Budget-owner is a grantor role covering AI model spend and cloud resource spend, with no departments in v1. The admin may act as budget-owner in small deployments and may override or approve budget.
- **D26 Skills are person-owned; visibility rules (Nov 1).** Every skill has a person holding `content-owner`. A private skill can be assigned only to agents its owner has authority over (their personal agents or team agents where they hold `accountable-lead`); a public skill can be adopted by anyone.
- **D27 Approver is the admission gate only (Nov 1).** Any signed-in user with factory access may submit an agent or skill draft. Three parallel gates run: automated security scan, automated compliance check, and budget availability (has the budget-owner allocated budget; skills need no agent budget per D28). The approver admits content once all applicable gates pass; the submitter has no say over budget, and no allocation on an agent means no admission.
- **D28 Skills spend the invoking agent's budget (Nov 1).** Skills hold no budget of their own; their spend counts against the agent that calls them.
- **D29 Run-time holds go to the content side (Nov 1).** Personal agent: only its one `content-owner` clears holds (an `agent-member` sub-role on a personal agent may only wake and converse). Team agent: any `member` (and `accountable-lead`) may clear a hold. The old requester and approver hold paths are removed.
- **D30 Team lead named at submission (Nov 1).** The submitter of a team agent names a known principal as its `accountable-lead` and does not become lead automatically; a personal agent's submitter becomes its `content-owner` (or the target user when an admin acts as that user).
- **D31 Skill hold policy and model binding (Nov 1).** A skill declares which of its actions need a human by default; the owner may make it stricter. Each skill's model is a factory-side binding the skill owner picks from evals, swappable and inherited by every calling agent; an agent's own model stays an ops/owner setting.
- **D32 Pre-provision by email and multi-email principals (updated Nov 1 walkthrough).** An admin creates a principal with 1..N emails (or creates a grant naming an email, creating the principal) before the person first signs in; on login from any configured IdP with a verified matching email, the principal and its grants are resolved. Ungranted callers outside granted domains still get `403` with no shadow record (D6).

## Stories (epic: factory-auth)

Story-breaker creates these as issues from this merged plan; each issue links back to [factory-auth.json](factory-auth.json).

- **S1 Canonical principal & multi-email directory:** Principal store mapping `user:<id>` (with display name) to 1..N globally unique lowercased emails; any configured IdP assertion with `email_verified: true` matching a mapped email resolves to that principal with zero claim-derived roles (unverified email claims refused); `cloudflare:`/`oidc:` strings in config-store owners, identity links and group members normalize to canonical principals; tests cover email case, multi-email aliases across IdPs, unverified-email refusal, and service-token CN.
- **S2 Grant store & domain grants:** Versioned store on the config backend supporting `user:<id>`, `domain:<domain>`, and `group:<id>` subjects, fleet/agent/skill scopes, optional expiry, and pending transfer states; `content-owner` scoped `{kind: agent | skill, id}`; unique owner constraint on personal agents and on skills; last-human-admin removal/downgrade refused (`409`); first verified sign-in under a granted `domain:<domain>` materializes the principal; non-admin grants to unknown subjects rejected before write (`403`, no ledger entry); fails closed on read error; e2e restart test.
- **S2b Agent types and ownership:** `kind: personal | team` on agents; personal: submitter (or `onBehalfOf` user) becomes the one `content-owner`; team: `accountable-lead` named at submission (submitter not lead automatically), `member` grants are separate, no `content-owner`, any `member` (or lead) may clear holds; existing agents classified in migration; provisioning works with operator/admin config grants alone.
- **S3 Grants API, act-as & MCP tools:** Routes for principals (add/remove mapped emails, admin-only) and grants guarded by `grants.manage` (fleet and `domain:<domain>` grants admin-only in v1); `content-owner` may grant content roles on their items and `accountable-lead` may add/remove `member` grants on their team agent (known principals/groups only); admin `actAs` (`onBehalfOf`) supported across user actions and ledgered with both `actor` and `onBehalfOf`; private skill assignable only to agents its owner controls; ceiling check rejects grants above granter's level; MCP tools call the same functions; `403` names required role.
- **S3b Content-ownership transfer:** Applies to personal agents and skills; dedicated endpoint writes `pending-revoked`/`pending-accepted` (7-day TTL) in one transaction; target notified; cancel/accept/decline endpoints plus sweeper rollback; team agents return `409`; old owner is read-only while pending (`403` on writes); on accept new owner gets write, old grant is revoked, and for personal agents `oauth-user` tokens (`ConnectionKeymaster`) are purged and outgoing-owner private skills detached (static `credentials.agent.*` kept); admin can execute departed-owner transfers via `actAs`; all ledgered.
- **S4 Single enforcement:** Route table with declared privilege per route; only routes in the route-exception registry (S14) omit a privilege; all admin helpers call `authorize()`; conformance test fails on any route with no privilege or any `FACTORY_ADMIN_EMAILS`/`FACTORY_TOKENS` read; `DERIVED_ROLE_PRIVILEGES` updated for `content-owner`, `accountable-lead`, and `member`; `approver` privileges limited to content admission.
- **S5 Factory API keys:** Issue/rotate (with optional `graceSeconds` overlap)/revoke/list; person device keys owned by `user:<id>` with unique active `(owner, deviceFamily)` and live intersection against owner's grants on every request; machine keys owned by `service:<name>` (`ingest`, `gatekeeper-egress`, `gatekeeper-ingress`, `break-glass`, health); `expiresAt` optional (`null` non-expiring allowed); admins may manage keys on behalf of any user (`actor` + `onBehalfOf` ledgered); hashed at rest (`fk_` prefix); shown once; revoked key refused on next request; never logged.
- **S5b API-key Access bypass:** Landing zone bypasses Access on `/api/v1` and `/mcp` only for requests carrying a `fk_` factory bearer key, still only via the proxy; conformance test holds no other bypass besides webhooks; keyless requests still hit the login/Access gate.
- **S6 Bootstrap, break-glass & lockout recovery:** `FACTORY_BOOTSTRAP_ADMIN` seeds only when zero admins exist; setup configures trusted IdP(s) (Google, Meta, Cloudflare, OIDC) with optional `allowedDomains` per deployment, ledgered, refusing to finish without one; non-expiring `service:break-glass` key sealed in Secrets Manager (`BREAK_GLASS_USED` ledgered + Console banner until rotated); out-of-band `bcl-aws` recovery command works any time with cloud IAM access (even if an unreachable admin grant exists), appending `LOCKOUT_RECOVERED` without printing secrets.
- **S7 Audit:** All principal, email-alias, domain-grant, grant, key, transfer, break-glass, recovery, and `actAs` (`actor` + `onBehalfOf`) actions ledgered, plus `CONTENT_SUBMITTED`, `GATE_PASSED`/`GATE_FAILED`, `CONTENT_ADMITTED`, `BUDGET_ALLOCATED`, `HOLD_CLEARED` (with who cleared it) and `OWNER_CONVERTED`; route `AUTHZ_DENIED` includes privilege and resource (`authz/check` preflight stays side-effect-free); secret-scan test passes.
- **S8 Migration import + shadow:** Importer converts `FACTORY_ADMIN_EMAILS`, `FACTORY_TOKENS`, identity-link roles (stripping authority from links), and `S18` owners into principals, grants, and keys; shadow mode compares old and new decisions (including hold routing and owner checks), ledgers mismatches, and exposes an admin readiness report requiring zero mismatches before cutover (configurable soak window).
- **S9 Clients:** Console removes anonymous `viewer` fallback, gates on `whoami` and `authz/check`, adds People (multi-email & domain grants), Keys, Submit/Drafts, Holds Inbox, Approver Admission Queue, Budget Allocation view, break-glass banner, and Admin Act-As banner; CLI gets `factory grants`, `factory keys`, and `--as`; `/mcp` filters `tools/list` by live privileges.
- **S10 Ops repo cutover:** `submind-aws` scripts (`factory-api.sh`, `aws-deploy.sh`, `identity-link.sh`, `config-agent-e2e.sh`) use factory API keys (`BREAK_GLASS_KEY` / deploy key) via `bcl-aws`; `FACTORY_TOKENS`/`FACTORY_TOKEN` and shared Access service token retired; deploy check proves an anonymous request gets the factory login page and every other route refuses it.
- **S11 Widen the door:** After cutover, if Cloudflare remains a configured IdP, Access admits verified identities for the configured IdP (and optional `allowedDomains`) while otherwise the factory login page handles OAuth directly (D16/D19); unconfigured IdPs and unverified emails are refused; ungranted identities outside `domain:<domain>` grants get `403` everywhere but `whoami`; onboarding needs no Cloudflare change.
- **S12 Login page and session:** Factory serves a standalone login page listing the IdPs configured at setup; OAuth with state/PKCE protection requiring `email_verified: true`; issues `HttpOnly` factory session cookie and `POST /api/v1/auth/logout`; console and `/ui` served only to a valid session; ledgered `SIGN_IN`/`SIGN_OUT`.
- **S13 CLI login flow:** `factory login --url` opens the login page; `"cli"` device-family key returned on a local loopback port; no pre-credential fetch; works across configured IdPs.
- **S14 Route-exception registry + test:** One registry names the login page, state-protected OAuth callbacks, and signature-verified webhooks with their protection; conformance test fails any other route reachable without a credential or declaring no privilege.
- **S15 Webhooks fail closed:** GitHub and generic `/api/v1/hooks/:id` refuse every delivery when no signature secret is set; signature checked before any other handling; e2e tests for missing, bad and good signatures.
- **S16 Health behind keys:** `/`, `/healthz`, `/api/v1/health` and metrics require a session (returning login page on `/` for browsers) or verified machine API key; load-balancer probes use a private internal listener or probe key.
- **S17 Retire CLI discovery:** `/.well-known/factory-cli` and `auth/src/discovery.ts` removed; CLI uses the login page directly.
- **S18 Owner conversion:** Before cutover, every production owner string (`cloudflare:<email>` in the config store) maps to a canonical principal (`user:<id>`) and `content-owner` (or `accountable-lead` for team-classified fleet agents) grant; dry-run report must show zero live personal agents without an owner and zero team agents without a lead before cutover.
- **S19 Budget-owner role:** One `budget-owner` per factory, a grantor not a reviewer; allocates AI model budget (`budgetUsd`, `policies/budget`) to agents outside the submission flow; `admin` can act as backup and override; skills hold no budget and spend against the invoking agent.
- **S20 Content submission + admission gates:** Any signed-in granted user submits an agent or skill draft; parallel automated security scan, automated compliance check, and (for agents) budget availability check run; `approver` admits only when all pass; submitter cannot set budget; replaces admin-decided registration and adoption.
- **S21 Interview agent drafting:** Interview helper endpoint/flow helps non-technical users assemble a valid agent/skill draft, which enters S20 unchanged.
- **S22 Holds to content side:** Run-time holds route exclusively to the personal agent's `content-owner` or to any `member`/`accountable-lead` on a team agent; requester and approver hold paths removed; e2e covers both agent types and personal-agent `agent-member` non-clearance.
- **S23 Skill default hold policy:** Skill manifest declares which actions hold by default (`hold: true | false`); adoption applies defaults and owners/leads may only make holds stricter, never looser.
- **S24 Per-skill model binding:** Factory-side binding from skill to model, set by the skill's `content-owner` (or admin) from evals, swappable without a manifest edit, and used for invocations of that skill while the agent's own model stays separate.

## Migration order

- **1. Shadow** Ship principal/grant/key stores, owner conversion dry-run (`S18`), and importer (`S8`): `FACTORY_ADMIN_EMAILS` -> admin principal & grant, `FACTORY_TOKENS` -> `service:<name>` keys, identity-link roles -> grants (leaving identity links as pure channel->principal mappings). Old and new decisions both computed; mismatches ledgered.
- **2. Cut over** Once `S18` dry-run shows zero orphaned live agents and `S8` shadow report shows zero mismatches, Bouncer switches to grants only (env lists warn only).
- **3. Keys** Ship `/api/v1` and `/mcp` key verification + Access bypass (`S5`, `S5b`). Seed `service:break-glass`, gatekeeper, and deploy keys into AWS Secrets Manager; cut over `submind-aws` scripts (`S10`); retire `FACTORY_TOKENS`/`FACTORY_TOKEN` and shared Access service token.
- **4. Door & Login** Ship factory login page, sessions, CLI loopback login, health-behind-keys, and retire `/.well-known/factory-cli` (`S12`–`S17`); widen/adjust Access or direct IdP sign-in (`S11`) so grants and `domain:<domain>` rules alone govern admission.
- **5. Remove** Delete legacy env role/token reads and `cloudflare-service:` role assumptions; enforce via conformance (`S4`, `R10`).

## Follow-on epic gaps: skill-driven egress

- **E1** Agent policy can hold routes no skill justifies, and those routes skip person-level role checks.
- **E2** Adopting a skill does not grant its routes, so an admin edits the policy separately.
- **E3** Nothing enforces a skill action's method, path or hold at egress; the gatekeeper sees only routes and hosts.

## Product flows walked through and confirmed (Dale Sackrider, Nov 1, 2026)

1. **Onboarding a new human (Confirmed):** Admin creates a principal with 1..N lowercased emails (e.g., both `stephaniesackrider@hotmail.com` and `stephanie.sackrider@gmail.com` on Stephanie's principal) and grants roles, or grants a role to `domain:<domain>` (e.g., `domain:sackrider.org`). Signing in through any configured IdP with `email_verified: true` on a mapped email resolves that principal; first verified sign-in under a granted domain auto-creates the principal. Only admins may pre-grant unseen emails; content-owners and team leads grant only to already-known principals (`403` with no write otherwise). Ungranted strangers get `403` everywhere except `whoami` with zero state written.
2. **Issuing, rotating and revoking a device key (Confirmed):** One active `fk_` key per `(owner, deviceFamily)` (e.g., Stephanie's `"tesla"` key scoped to `higgins`). `expiresAt` is optional (`null` non-expiring keys allowed). Admins can act as any user to issue/rotate/revoke keys (`actor` + `onBehalfOf` ledgered). Every request intersects the key's scopes with the owner's live grants; rotation supports optional `graceSeconds`; revocation cuts off the very next call (`401`). Machine-only roles use `service:<name>` principals.
3. **Transferring personal-agent ownership (Confirmed):** Two-phase `pending-revoked`/`pending-accepted` transaction (7-day TTL); old owner is immediately read-only while pending, restored cleanly on cancel/decline/expiry. On `accept`, all `oauth-user` tokens (`ConnectionKeymaster`) on that personal agent are purged (ledgered) and outgoing-owner private skills are detached (D26), while static `credentials.agent.*` secrets stay intact. Admins can complete transfers for departed owners via `actAs`.
4. **Granting team membership (Confirmed):** Team agents (`kind: "team"`) have no `content-owner`, one `accountable-lead` (named at submission; replaced only by `admin`), and `member` grants. Team leads (`accountable-lead`) can add and remove `member` grants (known principals/groups) on their own team agent. Any `member` (and lead) can converse with the team agent and clear its run-time holds (`HOLD_CLEARED` ledgers who cleared it).
5. **Break-glass use (Confirmed):** Non-expiring `service:break-glass` key sealed directly in AWS Secrets Manager (`factory/prod/BREAK_GLASS_KEY`, verified against the configured deployment AWS account via STS), used via `bcl-aws` + `factory-api.sh` with no browser/Cloudflare login and zero secrets printed. Every call writes `BREAK_GLASS_USED` to the ledger and raises a Console banner until rotated.
6. **Lockout recovery (Confirmed):** API blocks deleting or downgrading the last active human `admin` (`409`). `FACTORY_BOOTSTRAP_ADMIN` applies only when zero admins exist.
